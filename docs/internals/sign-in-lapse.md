# Lapsed sign-ins

`apps/server/src/infinitus/Layers/InfinitusSignInLapse.ts` (+ `infinitusSignInLapse.logic.ts`, tests) — lapsed AWS / gcloud sign-ins for the threads this server runs (#1076), the fork's counterpart to the Mac's transcript scan (retired with the terminal-session features, #1041), ported onto orchestrator v2 with #1627 (the v1 layer read the Claude driver's raw `item.updated` tool results; it left with the v2 merge, #1639, and AWS sign-in surfaced nowhere until the port).

**Source.** The layer tails `OrchestratorV2.streamDomainEvents` (the live tail the awareness relay uses: no replay from genesis, unbounded so a busy server drops nothing) and keeps the `turn-item.updated` events whose payload is a `command_execution` item. Every adapter normalizes its shell tool into that item — `input` is the command as typed, `output` its stdout and stderr once run — so the scan now covers every provider's Bash, not Claude's alone, and never reads an adapter's raw payload. The output is not head-capped before it is stored (the wire projection withholds it for RPC subscribers, not for this stream), so the tail the CLIs print their failure in is there to read. A subagent's command carries the child thread's id; that is the thread the need is logged against.

**Reading an item.** `signInFromTurnItem`: an item with `output` is read for a lapse (`signInLapse`); a `running` item with none is the command's start, read for a login the agent runs itself (`signInRun`); a finished command that printed nothing is neither — the adapter omits an empty `output`, so `output === undefined` alone cannot tell a start from a silent finish. The signatures are the Mac's marker and line-start tables (`AwsLogin.swift`, `GcloudLogin.swift`) ported verbatim: a marker anywhere plus one opening a line at column 0, so the same words quoted from a file or a grep hit never match; only the last 16 KiB is scanned. The profile is the error's own `--profile` when it prints one, else the command's `--profile` / `AWS_PROFILE` (`--account` / `CLOUDSDK_CORE_ACCOUNT` for gcloud), else `default`; gcloud's Application Default Credentials are the `application-default` account. A login the agent runs itself (`aws login`, `gcloud auth login`) blocks on a browser no client shows and prints no signature at all; only a login that opens a command segment counts — quoted spans are flattened to one word first, and a `--help` run is skipped — so a grep, an echo or a commit message carrying the words stays quiet; banyan's `bun scripts/agent-login.ts <aws|gcp>` counts as the CLI it wraps, its AWS default being the `banyan` profile (2026-09-22: a wrapped `gcloud auth login` opened a browser tab and no card).

**What a hit does.** On an app whose manifest lists the verb, the Mac's `aws-login <profile>` / `gcloud-login <account>` flow starts through `InfinitusService.command` (no `--pid`: a thread has no session pid; the Mac runs its default flow, and that path's post-write poll re-reads `aws-logins`, so the login reaches the web's and the phone's Sign-ins lists at once instead of at the next cycle) — unless that same reply already shows a login for the credential in flight (`hasLoginInFlight`: any `state.phase` short of `done`/`failed`), which is a browser tab waiting on a person and must not be taken over. The phones are rung once through the alert relay, deep-linked to the home screen's sign-in cards, whether or not the Mac could start the login. There is no row on the thread any more: v2 has no work-log row a reactor can leave, and no client drew the v1 `infinitus.signin.needed` row after the merge; the Sign-ins section and the push are the surfaces. Once per thread per profile per hour (a thread reaching two expired AWS profiles in one hour needs both logins); a login the agent runs itself is once per tool call instead — keyed by the item's id, since the same item is stored again as its presentation fills in — because it blocks on its own browser tab however recently the profile lapsed (2026-09-24: an agent's `aws login` twenty minutes after a lapse on the same profile raised no Mac login and no push). One sequential worker off the event stream, so the turn is never waited on; an unreachable Mac or a refused verb is logged.

**Ending the agent's own login.** The Mac's login then runs beside the agent's own, each CLI on its own localhost listener (gcloud takes 8085, the agent's the next free port), so signing in through the card never answers the agent's tab and its Bash call sat until its timeout (2026-09-23). The run is watched: the Mac's login is read with `--status` every 3 s while in flight, and once it is `done` the server ends the agent's login processes for that credential with SIGTERM (`agentLoginPids`: the CLI's own process — its Python running `aws login` / `gcloud.py auth login` — found only among this server's descendants in `ps`, so the Mac's own login, the app's child, and other servers' agents are out of reach). A Mac login already over at the first read is an earlier outcome and ends nothing; a failed one leaves the agent's login to its timeout. The output text and the command reach no log, span or payload — only the thread id, the provider and the profile.
