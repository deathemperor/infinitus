# Accounts page

`apps/web/src/routes/accounts.tsx`, `apps/web/src/components/accounts/` — the Accounts page: one group per connected environment that runs Infinitus, each `EnvironmentAccounts.tsx` owning that machine's snapshot, its flows in flight and its refresh, so the page never picks a machine and a remote machine's rows sit beside the primary's (the shell-run sign-ins below stay gated on the group being the primary environment, so the same page offers the shell path on this Mac's group and the link path on every other); a group whose connection is not `connected` says so instead of holding a skeleton. Inside a group: fleet sections, account rows and their actions, the forecast strip, the unavailable state (its Launch button targets that machine), and the Sign-ins section for lapsed AWS/gcloud credentials — `SignInsSection.tsx` with `signIns.logic.ts` — absent when nothing lapsed; one row per tool and profile, no session names and no `--pid` scope since the Mac's session sweep, #1041 — the phone's own `apps/mobile/src/features/infinitus/signIns.logic.ts` folds and words its rows the same way, and `InfinitusAwsLogin` carries neither `pid` nor `sessionLabel` any more, so an older app still sending them has them dropped at the boundary); row/section/sign-in models come from `packages/client-runtime/src/state/infinitusAccounts.ts`, whose `infinitusPageState` gates Accounts, Stats and Activity alike (#693): a server whose config arrived with `false` or without the field (`infinitusCapabilityOf`) gets the missing-adapter copy; a config that has not arrived waits like a missing snapshot, and Accounts folds every environment's answer together with `infinitusCapabilityAcross` to decide between the missing-adapter copy, the skeleton and the list of groups.

## Add account and sign in again

Add account and re-login (#671): a fleet whose capabilities carry `addOAuth` or `addCurrent` (swapd declares both since its `add-oauth`, #1530; the gate once read `addOAuth` alone and missed it, #1213) gets "Add account" in its header and "Sign in again" on a `relogin_required` row, both native's `add <fleet>` (the sign-in opens on the Mac), then the page polls `wait-add --timeout 5` until the app says the flow ended (`addAccount.logic.ts`); hidden on a build whose manifest lacks `add`.

## Sign-in inside the desktop app

On a build whose manifest lists `signin-begin` (#677) the sign-in runs inside the desktop app instead: the page sends `signin-begin <fleet> [--relogin <email>]` over `infinitus.command`, the desktop shell shows the OAuth page in a child `BrowserWindow` per flow (fresh in-memory `signin-<flowId>` partition, sandboxed, no preload — `apps/desktop/src/infinitus/InfinitusSignIn.ts`), the page polls `signin-status` every 2 s (`signIn.logic.ts`) and, for paste-code flows, takes the code from the success page — the shell hands it to the app over the control socket as `secret` (`submitInfinitusSignInCode`), so it never crosses an RPC, the server or the tunnel.

## Sign-in from any other client

On every other client (a browser, the tunnel, the desktop looking at a remote environment) the page is a link this device opens in a new tab and the code goes over `infinitus.secret` as `signin-code {flowId}` (#747 step 2): the field is `type="password"`, `autoComplete="off"`, cleared on submit and gone with the form; the CLI's own `error` is shown; the submitted value is never interpolated into any message. Closing the OAuth window never cancels; the page's Cancel sends `signin-cancel`. An engine that takes the OAuth redirect itself (`addOAuth`: swapd's `add-oauth`, the proxy) listens on the Mac's loopback, and a browser on this device is sent to _its_ localhost, where nothing listens — the case that used to need the owning Mac. So a headless `signin-begin` runs that engine's flow (never the CLI's paste-back one when the engine has it) and names the port as `redirectPort` in its reply and every `signin-status`; the page shows the same field for the address the browser ended on (`signInPasteField`: `address` only while `redirectPort` and `url` are both set — the shell's window on the primary Mac reaches the listener itself and never asks), sends it over the same `signin-code`, and the Mac replays it against `127.0.0.1:<port>` as one GET (`OAuthRedirectRelay`, `TokenFlow.submitRedirect`): the same path and query, which is all the listener reads, and only when the pasted value is a loopback URL on that port — never an address off the machine. The address carries the code, so it is a secret like the code was. The desktop stands in for the listener so there is nothing to copy (`apps/desktop/src/infinitus/InfinitusSignInRedirect.ts`, `listenInfinitusSignInRedirect` / `stopInfinitusSignInRedirect`): for a remote environment (`redirectSignIn`, never the primary one, where the engine itself holds the port) the page asks the shell to bind `127.0.0.1:<port>` (and `::1`, best-effort), open the page the #1213 way (a private browser window, else the plain default browser — never the child window, where a passkey sign-in never completes), answer the browser's one request with the engine's own words and hand the address back; the page sends it over `signin-code` and the flow's `redirectListening` hides the field. A port already held (`EADDRINUSE`: this Mac's own engine signing in, a proxy on 54545) or a refused hand-off flips `redirectListening` off with the error under the field, so the copy path is the fallback and never the first ask. The reply waits up to 15 s for the engine to redeem it and answers the engine's own refusal, so a stale or foreign address is a `codeError` under the field, not a stuck flow. Ahead of both, the sign-in the desktop shell runs itself (#1213): the engine is the OAuth client, so the shell spawns `swapd add-oauth` (next section) and the engine's own loopback listener catches the redirect — no code to paste, no Mac build to wait for, and a fleet whose `addOAuth` capability the app never advertised can still be signed into. Its two gates are the only ones (`fleetSignInGate`): the engine binary is where this client is (`shellOAuthSignIn`: the desktop bridge carries both methods and this is the primary environment) and the fleet's engine is the one whose sign-in is that flow (`fleetRunsShellOAuth`, `swapd`; the proxy engine declares `addOAuth` too and is not one). Not the `addOAuth` capability — gating on it once reproduced the very bug — and not the app's `signInRunning`, which is its word about a flow of its own. For the same reason the row model's `reloginNeeded` is the lapsed status alone; who may run a sign-in is the page's to decide. `FleetSection` renders it through the in-app branch — a shell flow has no `url` and no code field, so the same markup reads "Sign in in your browser." with a working Cancel — and `signIn.logic.ts`'s `SignInKind` says which half a flow belongs to, so start, cancel and end stay apart. The page opens in the system browser, not a child window: a passkey sign-in never completed in the child window (the platform authenticator is, as far as we can tell, the browser's and not an Electron window's), and the redirect lands on the engine's listener whichever browser rendered the page. There is no window to close, so only the page's Cancel or the engine's own timeout ends a flow the user walked away from; the browser tab shows the engine's "Signed in. You can close this window." In place of #677's per-flow cookie jar the page opens in the default browser's private window where its command line has a switch for one (`openInPrivateWindow`, the Mac app's `SignInSheetRoute` table: the Chromium family; Safari has none), so nobody signs out of the browser's account to add another; elsewhere the provider's page may offer the browser's current account first, and an account added twice lands in its existing slot (`slots::same_account`), so the worst case is a visible retry. A cancelled run answers `{ok: false}` with no `error`, and the page drops the flow rather than showing a failure the user caused.

## The sign-in the shell runs itself

`apps/desktop/src/infinitus/InfinitusOAuthSignIn.ts` (+ `InfinitusSwapdProcess.ts`, `infinitusSwapd.logic.ts`, test) — the sign-in the shell runs itself (#1213). **This is the one place the fork runs an engine's binary instead of talking to the Mac over the control socket**, and it bends "One API" on purpose: the OAuth client has to be whoever holds the PKCE verifier, and for a loopback redirect that is the engine. Signed off by the developer (2026-09-14), who put the consumer in the desktop app rather than `apps/mac`. `infinitusSwapd.logic.ts` is the pure half: `resolveSwapdBinary` (the `INFINITUS_SWAPD_CLI` override answers whole — a path only if it exists, empty meaning "no engine here" — then `/opt/homebrew/bin`, `/usr/local/bin`, `~/.cargo/bin`, `~/.local/bin`, then the menu-bar helper nested in the packaged bundle, #777) and `parseAddOauthLine`, which reads the two-line protocol `swapd --json --provider <p> add-oauth` streams: the URL line the loopback listener flushes when it binds, then the `{slot, email, created}` envelope the stored account prints, or the engine's own `{error:{code,message}}`. `InfinitusSwapdProcess.ts` is the spawn boundary (one `SwapdAddOAuthRun` with a `result` promise and a `stop`). `InfinitusOAuthSignIn.ts` is the service: `begin` resolves the binary, spawns the run, hands the URL to the system browser (`openInPrivateWindow`, then `ElectronShell.openExternal`; a refused open ends the run with "The browser could not be opened.") and races the announcement against a run that died before it, so a failure before the listener bound can never hang the page; `cancel` kills the run. One promise for the whole flow. The account is stored inactive (`slots::claim(activate = false)`), so a sign-in never switches the live login. Merged into `InfinitusDesktop.layer`; the methods are `beginInfinitusOAuthSignIn` / `cancelInfinitusOAuthSignIn` (`ipc/methods/infinitus.ts`, `channels.ts`, `DesktopIpcHandlers.ts`, `preload.ts`), their contracts `InfinitusOAuthSignInInput` / `-Result` in `packages/contracts/src/infinitus.ts` and the two optional `DesktopBridge` methods in `ipc.ts`. No token, no code and no email reaches a log or a span.

## Banked limit resets

Claude banks a few usage-limit resets per account (the CLI's `/reset`, program `cedar_ember`), and the fleet reads and spends them through the engine, never through the server's own Claude login (#1554; the per-environment path on Usage → Limits is #1553 and stays for a Claude connection that is not in a fleet). swapd asks the usage endpoint for the bank beside the windows under Claude Code's own agent string — the endpoint reports it to no other surface — and judges it at list time: `resets` on a row is what is left across the live grants, the grant the provider spends next and the hold on it (`notAtLimit`: it spends only while the account is at a limit; `cooldown`, with `until`; `blocked`: no spendable grant). Absent from a row with no live grant, so a client shows nothing rather than a zero. The Mac passes it through verbatim (`AccountResets`) and refuses `reset <fleet> <n>` for a row without a bank or with a hold; `swapd reset` re-reads the bank as that slot before the claim, since the CLI can spend one too. Every client shows the bank on the row and asks before spending — the Mac popup's ticket mark and row menu stage it like a row click stages a switch, and one popup-level alert commits it: the provider gives none back. `reset` is a write with the control socket's write budget (30 s); the claim itself may take up to 25 s on the provider's side plus two usage reads, so a slow one can outlive the budget the way `ignite` can — the row then shows the timeout copy while the app finishes, and the next snapshot carries the cleared windows. Never send a claim from a test or a probe: a spent reset is gone.
