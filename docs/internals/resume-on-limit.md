# Resume on limit

`apps/server/src/infinitus/Layers/InfinitusResumeOnLimit.ts` (+ `infinitusResumeOnLimit.logic.ts`) is resume-on-limit for the threads this server runs (#648), and since the sessions sweep (#1041) the only one left — the Mac's terminal nudge went with the sessions it typed into: the Claude adapter's parked-turn warning (`rate_limit_info.status: "rejected"`) or a limit-failed `turn.completed` records a stop (a parked turn's failed completion is the same stop ending, one row, the window kept); while any thread is stopped the layer subscribes to the snapshot and waits for the swapd fleet's active account — the one the plain CLI spends; the proxy fleets never count — to read `ok` from a probe taken after the stop (native's ResumeGate); a different account than the one at the stop counts on an older probe too, because swapd rations the usage endpoint and reads an idle account it just swapped to only minutes later.

swapd's `ok` is a credential status, not headroom (the account that just ran out reads `ok` on the next poll, which resumed a turn onto it every cooldown), so `resumeTarget` also reads the account's usage for the stop's window (`rateLimitType` on the stop): under 100 % counts, full does not; a reading without that window lets a different account through and the same one only once the stop's `resetsAt` passed. A failed stop names neither window nor reset (the CLI ends the turn with its synthetic rate-limit error and no rate-limit event, so `turn.completed` carries only `usageLimited`), so there the same account counts once a probe after the stop reads every window under 100 % — before that rule a thread whose account stayed live sat two hours past the window's reset with the account reading 20 %. Then the thread's CLI is stopped (a parked turn interrupted, a failed one's session stopped: a live process can keep spending the account it started on for minutes after a swap, and a turn sent into it was refused on the old account's limit again), a `infinitus.turn.resumed` work-log row names the account, and the thread continues with upstream's continuation prompt from its resume cursor.

The replace-then-send is one claim wide (#1509): `InfinitusLimitStops.setResuming` holds the thread from the interrupt or stop until the continuation has gone, because the session in between reports `ready` with no turn on it and the message queue's drain reads that as idle. Both sends then reached one session, the CLI answered one of the two turns, and the other stayed `running` as the session's active turn for as long as the thread lived — the row read "Working" and the idle reaper skipped it. The resume stands down for the same collision in the other order (`turnOvertookStop`: the thread has an open turn requested after the stop, its own parked turn excepted), rather than tearing that turn's CLI down. The full account, and what is still uncovered, is in `docs/internals/turn-queue.md`.

A parked stop is the account's whose usage the refusal's own `unifiedWindows` figures match (`refusedClaudeAccounts`), not blindly the live one's: a CLI keeps the login it started on for a while after a swap, and a refusal blamed on the account just swapped to reported a healthy account to swapd as spent until a weekly reset, which benched it 70 s after the swap. The live account when its reading agrees or nothing compares, else the single other account that does, else nobody, and an unnamed stop reports nothing to the engine.

The stop itself leaves an `infinitus.thread.limited` row ("Limit hit on <account>") and joins the layer's `InfinitusLimitStops.stopped` list (#270 I), which `ws.ts` merges into `subscribeInfinitusHolds` beside the held starts so the sidebar reads "Limit" with the account in the tooltip; the banner reads "Stopped on a usage limit" with no button; the resumed row or a new turn closes it. A parked stop's row and stream entry carry `resetsAt` (ISO) from the SDK's `rate_limit_info`; the SDK re-announces a parked turn as its reset moves, and the stream entry follows while the row stays as written; the tooltip and the banner add "resets <time>" in the user's timestamp format while the instant is still ahead (`infinitusHoldBanner.logic.ts` `limitedLine` / `resetLabelFor`, `sidebar/HeldTooltipText.tsx`). A failed stop names no reset.

A thread on an instance whose environment carries `ANTHROPIC_BASE_URL` (a proxy, #1088) spends no swapd account: its stop reads "Limit hit on the proxy instance <display name>", names no account, starts no snapshot watch and is never resumed — the banner stays until the user sends again. A failed stop outlives its session: the idle reaper (`ProviderSessionReaper`) stops a limit-stopped thread's session after half an hour, usually before the window resets, so `session.exited` ends only a parked stop, the restore on boot takes a `stopped` session as well as an `error` one, and the resume's send starts a new session from the resume cursor. Once per stop, 2-min cooldown per thread, a user turn cancels; off by the `infinitusResumeOnLimit` server setting (`apps/web/src/components/settings/infinitus/InfinitusResumeCard.tsx` on Settings › Menu bar).
