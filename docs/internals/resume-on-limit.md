# Resume on limit

`apps/server/src/infinitus/Layers/InfinitusResumeOnLimit.ts` (+ `infinitusResumeOnLimit.logic.ts`, `Services/InfinitusLimitStops.ts`) is resume-on-limit for the threads this server runs (#648), on orchestrator v2 since #1627: a Claude turn stopped by a usage limit continues on the account swapd swaps to, before the window resets. Upstream's own recovery (`UsageLimitRecoveryWorker`, the `autoResumeLimitedThreads` setting) re-sends at the reported reset; this layer resumes earlier, when another account has room. Off by the `infinitusResumeOnLimit` server setting (Settings › General beside upstream's row; the phone's Settings › Threads), which keeps the pill and drops the report and the resume.

## What a stop is on v2

Two things record a stop, both structured, never the notice's prose (#1107: the CLI's `blocking_limit` is its prompt-too-long gate and is classed `provider_error` with the context-window wording; matching "usage limit" text once armed a resume into a full context):

- **Parked**: the SDK's `rate_limit_event` with `status: "rejected"` on a running root turn. The adapter keeps the turn open (the CLI retries as the window resets) and tells the layer through its `onUsageLimitRefusal` hook — `ClaudeUsageLimitRefusal`: thread, run, `rateLimitType`, `resetsAt` in ms — which `ClaudeDriver` wires to `InfinitusLimitStops.reportRefusal` when the service is in context. Upstream's one `system_notice` per window is the thread's row; the CLI's synthetic "You've reached your … limit" assistant frame (`error: "rate_limit"`, re-sent on every retry) is kept off the thread by the adapter (#1320), its bookkeeping — the flag the failure's class reads — untouched.
- **Failed**: a `run.updated` whose thread shell then reads `status: "failed"`, `lastErrorClass: "usage_limit"` (the CLI gave up; `usageLimitResetAt` is the shell's). A parked turn ending this way is the same stop: one entry, the window kept, nothing reported twice. These are also restored at boot from the shell snapshot, with no account named.

A stop joins `InfinitusLimitStops.stopped`, which `ws.ts` streams as `subscribeInfinitusLimitStops` (`InfinitusLimitStop`: thread, kind, since, account, resetsAt, proxy). The clients fold every environment's list into `infinitusLimitStopsAtom` (`packages/client-runtime/src/state/infinitusLimitStops.ts`) and read it per row: the sidebar's and the phone's status resolvers take `limitStopped`, so a parked turn — "running" to the orchestrator — reads "Limited" like upstream's failed one, with `limitStopLine` ("Limit hit on <account> · resets <time>") in the pill's title and on the phone's detail line. A thread on an instance whose environment carries `ANTHROPIC_BASE_URL` (a proxy, #1088) spends no swapd account: its stop names the proxied instance, reports nothing and is never resumed.

## Whose limit it is (#1486)

The provider process keeps the token it started the request with, so a refusal landing seconds after a swap belongs to the account swapped _from_; blaming the live one benched a healthy account until the old one's weekly reset. `refusedAccount` compares the refusal's `resetsAt` for its `rateLimitType` with each account's reading of that window (`usage.fiveHour` / `sevenDay` / `scoped` by model word, `resetsAt` as the Mac and `swapd list --json` write it): the active account when its reading agrees within `RESET_MATCH_MS`, or when nothing can be compared (no reset on the refusal, no reading, no such window — today's behaviour); else the one other account whose reading matches; else nobody, and an unnamed stop reports nothing. The named account is reported to swapd at once (`limit-hit <account> --resets-at`, through the probe binary), since quota reads lag refusals by minutes.

## The resume

While any plain stop is open the layer subscribes to the Infinitus snapshot (the subscription is what makes the server poll; nothing stopped, nothing polled; the swapd probe answers while the menu bar app is away). `resumeTarget` is native's ResumeGate with headroom read where the engine reports it: an active account of the CLI-credentials fleet reading `ok` from a probe after the stop (a different account counts on an older probe), with the stop's window under 100 % — full does not count, whichever account, since the account that ran out reads `ok` on its next poll; without that window, a different account counts, and the same one once the reset passed or, for a stop naming no window, once every window reads under full. Once per stop, a 2-minute cooldown per thread.

The resume runs beside the worker (it waits on an event the worker delivers) and is the one function to rewire onto the queue lane's turn-start gate when `feat/v2-queue` lands: a parked run is `run.interrupt`ed (the adapter closes the CLI, which keeps the login it started on), and once `run.updated` records it ended, `message.dispatch` continues it as `manualContinuationOfRunId` with upstream's own "Continue where you left off." (`createdBy: "user"`, `creationSource: "server"`, the row the thread shows). A failed run is continued the same way at once; its process is replaced on that prompt by the adapter's `spentOnLimit` flag unless background work pins it. Each command re-reads the shell first — archived, settled, another run started (`latestRunId` moved, or `activeRunId` not the stop's) — and stands down; v2's settlement sweep settles on days of idleness or a merged PR and cannot race the dispatch the way v1's did (#1522), and a `thread.settled` drops the stop.

Restart (`claude --resume` into a fresh process) is the adapter's; the layer never touches provider state. The Mac side (swapd, `infinitusctl`) is unchanged.
