# Phone thread card

Retired with #1375. Until then the Mac drew the phone's lock-screen thread card with the user's own APNs key: the server folded every live thread's `projectThreadAwareness` into an aggregate and handed it to the Mac's `push` verb as `thread.activity` (`InfinitusAgentActivity.ts`, #1047 part 3), the phone registered its push-to-start and per-card tokens with the Mac over `activities-token` (`InfinitusThreadCardBridge`, #1047 part 2, #1265, #1277), and the Mac started and updated the card (`LiveActivityPusher`, `ThreadCardStart`). With Infinitus Connect self-hosted the relay's own pusher (`AgentAwarenessRelay` → `infra/relay`) draws the card with the relay's key, and the Mac's account alerts ride the same relay as thread-less pushes (`docs/internals/notifications.md`). The Mac's battle plan, which read the fold's active count as its busy-session signal (`desktopActiveThreads`), asks `GET /api/infinitus/running-turns` with its desktop credential instead (`AppModel.refreshDesktopActiveThreads`).

What stayed: the fork's hunk in `patches/expo-widgets@57.0.15.patch` (`onExpoWidgetsActivityUpdate`), with no consumer — drop it at the next expo-widgets bump rather than re-applying it (`docs/internals/fork-registration-points.md`).
