# The identifier rename

Issue #1368 (user ruling 2026-09-16) extends the product name to identifiers. Slice A made every user-facing string say Infinitus (`PRODUCT_NAME`, `CONNECT_NAME`); slice B renamed the relay's fork-owned infrastructure names; slice C is `scripts/infinitus-rename.ts`, one idempotent table of the identifiers the fork owns outright, so the rename is a script run — and so every upstream sync re-runs it.

## What the table renames, and why only that

The table holds the "safe to rename outright" set of the issue's compatibility checklist: names nothing outside this tree persists or reads. The workspace package scope (`@t3tools/*`, private), the CSS custom properties and Tailwind font utilities (`--t3-*`, `font-t3-*`), the wordmark component and the Connect surfaces (`T3Wordmark`, `T3Connect*`, `useT3ConnectAuthPrompt`, files included). Not `T3Mark`: that is T3's own artwork, which the upstream mobile variants keep (#1188). The test beside the script proves the table is idempotent (no entry's output matches any entry's pattern) and that the compat-read identifiers pass through untouched.

Everything a user's disk, an installed unit, a shipped build or an external service holds stays out of the table on purpose, because a blind rewrite there breaks an existing install: `T3CODE_*` / `T3_*` env vars (read sites take the new name with the old as fallback), `t3code:` localStorage keys and the two IndexedDB databases (migrate on read: `uiStateStore.ts` already has the legacy-key chain to extend), the `t3` binary and its release archive names (slice D, done: the executable and archive are `infinitus`; 0.5.0-alpha.20 was the one release that also carried the archive under the old name, with a `t3` symlink inside, for installs from before the rename), the `t3-code` MCP server id (slice E, done: the id is injected per launch, so the adapters just say `infinitus` now; what persists is the tool names in thread history, `mcp__t3-code__…`, which the two tool-name readers keep accepting), the server's `t3/…` Effect service tags (the language service's `deterministicKeys` rule derives them from `apps/server`'s package name `t3`, so they move with slice D's package rename), the launchd / systemd unit names, the `t3code` URL scheme, the `t3-env:` issuer and `t3-relay-dpop-access+jwt` typ, `/.well-known/t3/environment`, the Android notification tags, the Axiom dataset names (their tokens are baked into builds), the Expo slug and the upstream-variant mobile bundle ids and `modules/t3-*` native module ids. Each of those is its own slice with a legacy read at every site.

## Slice A: the product name

Every string a user reads says `${PRODUCT_NAME}`, and "T3 Connect" is `${CONNECT_NAME}` ("Infinitus Connect"), both from `productName.ts`, on every surface: web, mobile, server (CLI help and command descriptions, log lines, errors, HTTP and HTML pages, pairing and service copy, MCP tool descriptions, the git author name, the prompts and runtime instructions the assistant echoes), `packages/*` and `docs/user`. Never a literal "T3 Code" or "T3 Connect": the web and desktop guard tests, `scripts/connect-name.guard.test.ts` (server, phone, packages, relay) and the visual pass fail on a new one. Those guards read only `.ts`/`.tsx`, and upstream owns the `docs/user` pages and rewrites them on every sync, so `docs` is held by the rename table instead (`within`, `prose`): "T3 Code" becomes "Infinitus" under all of `docs/`, a bare "T3" only under `docs/user/` (in `docs/internals` a bare T3 is as often upstream's glyph, mark or Clerk instance as the product), the sync re-runs them on upstream's side, and CI's `--check` fails on a leftover. A `prose` entry spares the literals: a name inside or opening quotes or backticks (`T3 Code (Alpha)`, "Built on T3 Code", a `codesign` path) and one after "real" or "upstream's" — write a sentence about the other product in one of those forms, or the next run renames it. The same three guards fail on a bare "T3" used as the product noun ("T3 Account", "Open T3", "a T3 thread"; identifiers never match), with an allowlist for the wordmark glyph, the relay's live column default, `McpHttpServer.ts`'s `T3-Mode-Limit` header and the triage playbook (`triage/triagePrompt.ts`) that must stay byte-identical to upstream's file; "T3 Chat", upstream's separate product whose plan the relay can link, passes all three. Identifiers were out of this slice's scope and followed in slices B–E. One literal stays by necessity: the lock-screen widgets say "Infinitus", because a widget body serializes into the extension and cannot reach an imported constant. Translatable copy is the other: the English inside `msg()`, `gt()` and `<T>` must be a literal for the gt CLI, so it says "Infinitus" and "Infinitus Connect" outright (below).

## Slice B: the relay's own names

The relay's fork-owned identifiers are `infinitus-relay`: the package name, the `--filter` in `deploy-relay.yml` and the README, the `infinitus-relay/<dir>/<Name>` Effect service tags, and the Clerk JWT template and audience that `docs/operations/02_connect-setup.md`, the example env files and the test fixtures name. Two names stay on purpose. The Alchemy stack is still `T3CodeRelay`: Alchemy's state rows key on the stack name, and a fresh stack looks the retained Neon project up by a generated name, so a rename orphans the database and creates a second project. The Axiom dataset and token names stay `t3-code-relay-*` because their tokens are baked into shipped builds; the OTel `service.name` the worker reports is `infinitus-relay-worker`. `infra/relay/src/http/Api.ts` reads `CLERK_JWT_AUDIENCE` as a comma-separated list (`expectedClerkAudiences`), which is how the deployed relay verified tokens from the old and the new Clerk template through the cutover; production now lists `infinitus-relay` alone. The root `.env.example`'s Clerk block is the fork's since #1322 (no upstream values, filled in once the relay is deployed), and upstream's disabled `release.yml` still says `t3code-relay` until the codemod sync renames it.

## Translatable copy

Upstream v0.1.11 wrapped its UI copy for translation (`docs/internals/14_i18n.md`), and the catalogs key each string by a hash of its English. Branding that copy on the fork's side would leave keys upstream's catalogs lack, on every sync. So the table's `copy` entries rename "T3 Code", "T3 Connect" and a bare "T3" (not "T3 Chat" or "T3 Tools") on upstream's side, but only inside the English of a `msg()` or `gt()` call or a `<T>` element under the roots the gt CLI scans, and inside the strings of the catalogs. Everything else there keeps its literal: comments, the V1 profile names, values passed as `{product}` (those take `PRODUCT_NAME` or `CONNECT_NAME` in the merge). `scripts/infinitus-rename-catalogs.ts` then regenerates each app's catalogs and gives each moved key the translation its English had. It runs after `vp fmt`, because fmt can re-wrap a `<T>` element's text and move its key again. Tests that assert rendered English are not renamed, so re-flip them in the merge. A `t3` command named in copy is still upstream's (`t3 serve`); that's open.

## Slice D: the `infinitus` binary and archive

The executable and the release archive are named `infinitus`: `scripts/build-cli-archive.ts` (stem and executable), `scripts/smoke-cli-archive.ts`, `scripts/build-desktop-artifact.ts` (`wslRuntimeArchiveStem`, the WSL runtime's entry), `packages/shared/src/cliRelease.ts` (`cliArchiveFileName`), `apps/server/src/cloud/pinnedRuntime.ts` (`entryPath`, and the launcher script `findPosixLauncher` looks for and `writePosixLauncher` writes), `apps/server/src/cli/invocation.ts` (`PINNED_RUNTIME_ENTRY`, which still matched a `t3` executable until v0.1.10's sync, so a downloaded runtime's launcher was never detected), `packages/ssh/src/tunnel.ts` (the remote runner script), `apps/desktop/src/wsl/DesktopWslEnvironment.ts` (the probe and install scripts), `apps/server/src/cli/update.ts` (`infinitus.cmd`, and with `service.ts`, `connect.ts`, `pair.ts`, `uninstall.ts`, `cloud/bootService.ts` and `cloud/selfUpdate.ts` the command names in user-facing copy), the installers (`docs/internals/release-and-updates.md`) and `infinitus-release.yml`'s `publish` job. 0.5.0-alpha.20 alone also attached each archive under its old name with a `t3` symlink inside, so an install from before the rename could update; #1399 closed that window, and an older install updates to alpha.20 first. The `t3` package name and `bin` in `apps/server/package.json` stay: they are the npm identity, and the Effect service tags follow them. The rename is re-applied on every sync together with its fixtures: `cliRelease.test.ts`, `pinnedRuntime.test.ts`, `selfUpdate.test.ts`, `service.test.ts`, `update.test.ts`, `invocation.test.ts`, `uninstall.test.ts`, `install.test.ts`, `scripts/install.test.ts`, `tunnel.test.ts`, `DesktopWslEnvironment.test.ts` and `build-desktop-artifact.test.ts`.

## Applying it

The rename landed in one PR (~2,450 files; the open branches at the time merged main and re-ran the script on their side): `node scripts/infinitus-rename.ts`, `pnpm install` (the lockfile's `workspace:*` specifiers carry the new scope), `vp fmt` on the changed files (the longer scope re-wraps lines and re-sorts `package.json` dependencies), the typechecks and the test suites. `node scripts/infinitus-rename.ts --check` is the guard from then on: it fails while any old identifier is in the tree, and `ci.yml` runs it.

## The sync rule

Once the rename has landed, an upstream merge would conflict on every renamed line. The rule that keeps merges small: on each sync, branch from `upstream/main`, run the script THERE (`git show main:scripts/infinitus-rename.ts` — the script is the fork's, upstream has none), then `vp i --no-frozen-lockfile` (the lockfile's peer-set hash for the mobile native modules changes with the scope), `vp fmt` on the changed files and `node scripts/infinitus-rename-catalogs.ts` (from `main` too), commit, then merge that branch into the sync branch. Both sides then carry the same names and the merge's conflicts collapse to real changes. The renamed commit is parented on the previous renamed commit in `main` as well as on `upstream/main` (`git commit-tree`), so the sync's merge base is itself a renamed tree: with upstream's tip as the only parent, the base was the unrenamed commit and every fork edit beside a renamed line conflicted, ~130 files a day (#1538, #1543). `upstream-sync.yml` does exactly this once `--check` passes on `main`; before that it merges upstream unrenamed. Never "take upstream's file and re-run the script": that drops the fork's registration-point edits in that file.
