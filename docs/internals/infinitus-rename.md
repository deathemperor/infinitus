# The identifier rename

Issue #1368 (user ruling 2026-09-16) extends the product name to identifiers. Slice A made every user-facing string say Infinitus (`PRODUCT_NAME`, `CONNECT_NAME`); slice B renamed the relay's fork-owned infrastructure names; slice C is `scripts/infinitus-rename.ts`, one idempotent table of the identifiers the fork owns outright, so the rename is a script run — and so every upstream sync re-runs it.

## What the table renames, and why only that

The table holds the "safe to rename outright" set of the issue's compatibility checklist: names nothing outside this tree persists or reads. The workspace package scope (`@t3tools/*`, private), the CSS custom properties and Tailwind font utilities (`--t3-*`, `font-t3-*`), the wordmark component and the Connect surfaces (`T3Wordmark`, `T3Connect*`, `useT3ConnectAuthPrompt`, files included). Not `T3Mark`: that is T3's own artwork, which the upstream mobile variants keep (#1188). The test beside the script proves the table is idempotent (no entry's output matches any entry's pattern) and that the compat-read identifiers pass through untouched.

Everything a user's disk, an installed unit, a shipped build or an external service holds stays out of the table on purpose, because a blind rewrite there breaks an existing install: `T3CODE_*` / `T3_*` env vars (read sites take the new name with the old as fallback), `t3code:` localStorage keys and the two IndexedDB databases (migrate on read: `uiStateStore.ts` already has the legacy-key chain to extend), the `t3` binary and its release archive names (slice D, done: the executable and archive are `infinitus`; 0.5.0-alpha.20 was the one release that also carried the archive under the old name, with a `t3` symlink inside, for installs from before the rename), the `t3-code` MCP server id (slice E, done: the id is injected per launch, so the adapters just say `infinitus` now; what persists is the tool names in thread history, `mcp__t3-code__…`, which the two tool-name readers keep accepting), the server's `t3/…` Effect service tags (the language service's `deterministicKeys` rule derives them from `apps/server`'s package name `t3`, so they move with slice D's package rename), the launchd / systemd unit names, the `t3code` URL scheme, the `t3-env:` issuer and `t3-relay-dpop-access+jwt` typ, `/.well-known/t3/environment`, the Android notification tags, the Axiom dataset names (their tokens are baked into builds), the Expo slug and the upstream-variant mobile bundle ids and `modules/t3-*` native module ids. Each of those is its own slice with a legacy read at every site.

## Slice B: the relay's own names

The relay's fork-owned identifiers are `infinitus-relay`: the package name, the `--filter` in `deploy-relay.yml` and the README, the `infinitus-relay/<dir>/<Name>` Effect service tags, and the Clerk JWT template and audience that `docs/operations/connect-setup.md`, the example env files and the test fixtures name. Two names stay on purpose. The Alchemy stack is still `T3CodeRelay`: Alchemy's state rows key on the stack name, and a fresh stack looks the retained Neon project up by a generated name, so a rename orphans the database and creates a second project. The Axiom dataset and token names stay `t3-code-relay-*` because their tokens are baked into shipped builds; the OTel `service.name` the worker reports is `infinitus-relay-worker`. `infra/relay/src/http/Api.ts` reads `CLERK_JWT_AUDIENCE` as a comma-separated list (`expectedClerkAudiences`), which is how the deployed relay verified tokens from the old and the new Clerk template through the cutover; production now lists `infinitus-relay` alone. The root `.env.example`'s Clerk block is the fork's since #1322 (no upstream values, filled in once the relay is deployed), and upstream's disabled `release.yml` with `docs/operations/release.md` and `docs/operations/android-notifications.md` still say `t3code-relay` until the codemod sync renames them.

## Slice D: the `infinitus` binary and archive

The executable and the release archive are named `infinitus`: `scripts/build-cli-archive.ts` (stem and executable), `scripts/smoke-cli-archive.ts`, `scripts/build-desktop-artifact.ts` (`wslRuntimeArchiveStem`, the WSL runtime's entry), `packages/shared/src/cliRelease.ts` (`cliArchiveFileName`), `apps/server/src/cloud/pinnedRuntime.ts` (`entryPath`), `packages/ssh/src/tunnel.ts` (the remote runner script), `apps/desktop/src/wsl/DesktopWslEnvironment.ts` (the probe and install scripts), `apps/server/src/cli/update.ts` (`infinitus.cmd`, and with `service.ts`, `connect.ts`, `pair.ts`, `uninstall.ts`, `cloud/bootService.ts` and `cloud/selfUpdate.ts` the command names in user-facing copy), the installers (`docs/internals/release-and-updates.md`) and `infinitus-release.yml`'s `publish` job. 0.5.0-alpha.20 alone also attached each archive under its old name with a `t3` symlink inside, so an install from before the rename could update; #1399 closed that window, and an older install updates to alpha.20 first. The `t3` package name and `bin` in `apps/server/package.json` stay: they are the npm identity, and the Effect service tags follow them. The rename is re-applied on every sync together with its fixtures: `cliRelease.test.ts`, `pinnedRuntime.test.ts`, `selfUpdate.test.ts`, `service.test.ts`, `tunnel.test.ts`, `DesktopWslEnvironment.test.ts` and `build-desktop-artifact.test.ts`.

## Applying it

The rename landed in one PR (~2,450 files; the open branches at the time merged main and re-ran the script on their side): `node scripts/infinitus-rename.ts`, `pnpm install` (the lockfile's `workspace:*` specifiers carry the new scope), `vp fmt` on the changed files (the longer scope re-wraps lines and re-sorts `package.json` dependencies), the typechecks and the test suites. `node scripts/infinitus-rename.ts --check` is the guard from then on: it fails while any old identifier is in the tree, and `ci.yml` runs it.

## The sync rule

Once the rename has landed, an upstream merge would conflict on every renamed line. The rule that keeps merges small: on each sync, branch from `upstream/main`, run the script THERE (`git show main:scripts/infinitus-rename.ts` — the script is the fork's, upstream has none), then `vp i --no-frozen-lockfile` (the lockfile's peer-set hash for the mobile native modules changes with the scope) and `vp fmt` on the changed files, commit, then merge that branch into the sync branch. Both sides then carry the same names and the merge's conflicts collapse to real changes. `upstream-sync.yml` does exactly this once `--check` passes on `main`; before that it merges upstream unrenamed, as today. Never "take upstream's file and re-run the script": that drops the fork's registration-point edits in that file.
